1. Two independent dimensions and Bridge

The application has two dimensions: the kind of shape and the rendering method.
Circle stores a radius; Square stores a side. VectorRenderer, RasterRenderer, and
AsciiRenderer produce different descriptions of the same shape data. The required
samples are a circle with radius 2 and a square with side 3. [1]

Shape is the abstraction, Circle and Square are refined abstractions, and Renderer
is the implementor interface. Shape holds a private Renderer reference received
through its constructor. Circle.execute() delegates to renderCircle(radius), and
Square.execute() delegates to renderSquare(side). Main creates and connects the
objects. Shapes manage their domain data; renderers manage the output style.

Bridge fits because shape behavior and rendering style vary separately. It lets
one Circle work with any Renderer without a CircleVector or CircleRaster subclass.
This use follows the independent-variation intent described in the Bridge reading.
[2] The relationship uses an interface-typed object reference and composition.

3. Five annotated Clean Code excerpts

a. Separation of responsibilities - Circle.java and VectorRenderer.java

    public String execute() {
        return getImplementation().renderCircle(radius);
    }

    public String renderCircle(int radius) {
        return "VECTOR circle radius=" + radius;
    }

Circle selects the operation and supplies its radius. VectorRenderer creates the
vector description. The shape does not contain vector, raster, or ASCII formatting.
This separation keeps output changes out of domain classes.

b. Meaningful names - Main.java, checkRuntimeSwitch()

    boolean sameObject = original == switched;
    boolean stateUnchanged = originalId.equals(switched.getId())
            && originalRadius == switched.getRadius();

The names show exactly which properties are being checked. sameObject checks
reference identity; stateUnchanged checks the ID and radius. These names make the
runtime-switch proof easy to understand without confusing an ID with an object.

c. Small focused methods - Shape.java

    public void setImplementation(Renderer implementation) {
        this.implementation = implementation;
    }

This method only replaces the renderer reference. It does not recreate the shape
or modify its ID or dimension. A single responsibility makes its effect easy to
trace during the defense.

d. Avoidance of duplication - Main.java

    private static int checkResult(String testId, String classes,
                                   Shape shape, String expected) {
        String actual = shape.execute();
        boolean passed = expected.equals(actual);
        return printCheck(testId, passed, classes + " | result=" + actual,
                "result=" + expected);
    }

T1-T4 and T6-T7 reuse the same execute/compare/report workflow. printCheck also
centralizes the PASS/FAIL output for T5 and the other checks. Fixing the reporting
logic therefore does not require copying a change into every demonstration case.

The renderer methods intentionally stay simple: each describes a different shape
and implementation. No shared rendering superclass is needed for one-line outputs.

e. Encapsulation of state - Shape.java and Circle.java

    private final String id;
    private Renderer implementation;

    private final int radius;

    public int getRadius() {
        return radius;
    }

Private fields prevent direct external changes. final keeps the ID and radius
unchanged after construction. The renderer is the intentionally replaceable field,
accessed by subclasses through the protected interface-typed getter. Square uses
the same approach for its side. This protects domain data during switching.

5. Trade-off and comparison with Adapter

Bridge introduces an interface and a level of delegation. In this small drawing
application, that adds classes compared with putting every output in each shape.
The shape-specific Renderer contract is easy to understand, but adding a completely
new shape would require another operation and corresponding renderer methods.
Adding a new renderer, as shown by AsciiRenderer, leaves the existing contract and
shape classes unchanged. The independence is within the operations of that contract.

Bridge supports independent variation of abstractions and implementations. Adapter
makes an incompatible existing interface usable through the interface a client
expects. [2, 3] Here the renderers already share Renderer. There is no incompatible
API being translated. An adapter would be useful if a future external drawing
library had a different API and needed to be wrapped behind Renderer.
